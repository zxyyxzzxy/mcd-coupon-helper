# 场景 E：积分管家

> **何时读本文件**：用户说「我的积分」「麦享会积分」「积分快过期了」「积分能换什么」「积分商城」。
> **不适用**：问优惠券的走 `coupon-claim.md` / `coupon-wallet.md`；问别的品牌积分（信用卡、话费）不要用本流程。

积分是麦享会体系里的资产，和优惠券是**两套独立的东西**。券会过期，积分也会过期，而且过期的积分**不会提醒你**——这是本场景存在的理由。

---

## 四步流程

### 第 1 步：拉账户

调 `query-my-account`（无参数）。返回 JSON，字段全部是**字符串**，用前要转数字：

| 字段 | 含义 | 单位 |
|---|---|---|
| `availablePoint` | 当前可用 | 分 |
| `accumulativePoint` | 累计获得 | 分 |
| `usedPoint` | 已使用 | 分 |
| `expiredPoint` | **已过期（已浪费）** | 分 |
| `currentMouthExpirePoint` | **本月将过期** | 分 |
| `nextMouthExpirePoint` | 下月将过期 | 分 |
| `lastMouthExpirePoint` | 上月已过期 | 分 |
| `frozenPoint` | 冻结中 | 分 |

校验一下账能不能对上：`availablePoint + usedPoint + expiredPoint ≈ accumulativePoint`。对不上就如实说明存在冻结或统计口径差异，不要硬凑。

### 第 2 步：算两个数

- **浪费率** = `expiredPoint / accumulativePoint`。这是全场景最有冲击力的一个数字，一定要算并展示。
- **紧迫积分** = `currentMouthExpirePoint`（> 0 才需要提醒）。

### 第 3 步：查能换什么（仅在需要时调）

调 `mall-points-products`。按用户意图选类目：

| 用户问 | `catRuleIds` |
|---|---|
| 积分能换什么（默认） | `1>4`（商品券，最实用） |
| 有什么实物 / 周边 | `2>8` |
| 实物商品 | `2` |
| 派对 / 体验类 | `1>6>20,1>6>21,1>6>22` |

**必须过滤已下架商品**：返回里大量存在 `downTime` 已过、但 `status` 仍为 `2`（上架）的商品。实测 25 条商品券里有 **16 条已经过期却仍标着上架**（`downTime` 落在 2026-01-10、2026-03-21、2026-06-24），只有 9 条真正可兑。用当前时间比对 `downTime`，过期的直接剔除，不要展示给用户。

**必须讲清兑换的真实含义**：这些商品券不是「免费拿」，而是**用积分换取「以券面价购买该商品的资格」**。例如「6.9元香芋派/菠萝派任选」需 50 积分，含义是**花 50 积分 + 6.9 元**买这份派，不是 0 元白拿。展示时要把「所需积分」和「券面价」两列都列出来，避免用户误解。

### 第 4 步：给建议（这是本场景真正的价值）

按优先级：

1. **有本月将过期的积分** → 先找所需积分 ≤ 「本月将过期 + 可用」中**快过期那部分**能覆盖的兑换品，明确说「用这 50.1 分去换 X，本月过期前用掉」。
2. **最便宜的兑换品都换不起** → 直说还差多少分，**不要**建议充值、购买或第三方刷分。
3. **有已过期积分** → 用一句话点出来（"累计 2277.8 分里有 1107.7 分已经过期"），陈述事实，不要说教。
4. **积分充足且无临期** → 只报账 + 给一句「暂时不用动」，不要为了显得有用而硬推兑换。

## 输出模板

```
💡 你的麦享会积分：可用 891.1 分

| 项目 | 积分数 |
|---|---|
| 当前可用 | 891.1 |
| 累计获得 | 2277.8 |
| 已使用 | 279.0 |
| 已过期 | 1107.7 |
| 本月将过期 | 50.1 |

⚠️ 累计获得的积分里有 48.6%（1107.7 分）已经过期浪费，实际只用掉了 12%。

可兑换（商品券，已剔除下架）：
| 商品 | 所需积分 | 状态 |
|---|---|---|
| ... | ... | 可兑换 / 积分不足（差 X 分） |

建议：本月 50.1 分会在月底过期，可优先换 X（需 Y 分）。
```

## 铁律

1. **积分单位是「分」，不是人民币。** 写「891.1 分」，绝不写成「¥891.1」，也不要按 1:1 折算成钱——兑换比例不固定。
2. **不擅自兑换。** `mall-create-order` 是写操作，会真实扣分并生成订单，必须用户明确说「帮我换」并确认商品后才可执行。
3. **不催、不推。** 积分没临期就说暂时不用动。这个 Skill 的可信度来自「不乱建议」。
4. **过期商品必须过滤。** 见第 3 步，直接展示下架商品会让用户白跑一趟。
5. **账户 ID 不输出。** `accountId` 属于账号信息，展示积分时不需要它。

## 实测基准（2026-10-20，可用于自检）

| 项 | 值 |
|---|---|
| 可用 / 累计 / 已用 / 已过期 / 本月将过期 | 891.1 / 2277.8 / 279 / 1107.7 / 50.1 |
| 商品券总数 | 25 条 |
| 其中真正可兑（`downTime` 未过） | **9 条** |
| 过期却仍标上架的 | **16 条** |
| 有效档位 | 50 / 100 / 200 / 500 / 800 积分 |

如果解析出来只有 2-3 条可兑，多半是过滤条件写错了（比如拿 `status` 当有效判据）。
